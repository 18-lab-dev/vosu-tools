# Replay renderer

Interfaces: **UI + CLI**. The native rendering backend starts on demand and stops when idle; it has no separate service controls or startup toggle.

`vosux replay-renderer render /absolute/play.osr --set mania.scroll_speed=27 --set background_dim=0.9 --resolution 2560x1440 --out /absolute/play.mp4`

`--out`, `--fps` and `--resolution` are optional; the last two default to the tool's settings. Without `--out`, the video is named after the replay and goes into the output folder. A relative `--out` is resolved against the current directory.

The studio is simple by default: add replays, pick an output size, press **Render MP4**; layout (Auto), skin (the client's current skin), HUD and timing follow sensible defaults. Each track card shows its player, map and **Skin** (a new skin applies at once); its **More** disclosure holds the track's layer switches and render settings (**Apply** to use them, **Save preset** to keep them for the player). The Output panel's **Advanced** disclosure holds frame rate, outro and fade, and skin imports. Placement is edited on the preview (see Layout editor); the selection's fields appear only while something is selected. None of these settings modifies osu! or changes the recorded key/cursor input or judgement windows. The Timeline panel's expand button opens the same track list in a large dialog (Escape or a click on the dimmed backdrop closes it).

## Maps and replays

A replay stores only its beatmap's MD5, so the exact difficulty must be installed locally. The service looks it up in two places, in this order:

1. **stable Songs**: the folder vosu reports for an attached stable client, or the tool's `osu_dir` / `songs_dir` settings. The folder is indexed by MD5 once and cached.
2. **lazer**: through the optional **Lazer library** tool (`lazer-library`), via `GET /tools/lazer-library/api/v1/beatmaps/by-md5/<md5>`. Files are read from lazer's hashed store, and only after checking that the `.osu` MD5 matches and that every path stays inside `<lazer>/files`. The library is an optional dependency: it is used only through its read routes, which any tool token may call, and it is not listed in `[[requires]]`, which would block the studio whenever it is missing.

If neither has the map, the service answers 404 with `{"code":"map_missing","md5","searched":[…]}`. The studio shows it above the preview: the MD5, every place searched, **Copy MD5**, and, when the Beatmap downloader is installed, **Find in downloader** (`/tools/downloader/#md5=<md5>`).

Replays come from stable's `Replays` folder and lazer's `exports` folder. The lazer folder is found from the attached lazer client, then the library's data folder, then the platform default (honouring `storage.ini`). For a given map, the list also includes lazer scores with replays from `GET …/v1/scores/by-beatmap/<md5>`. `GET /v1/replays` lists every replay, newest first. `GET /v1/replays?md5=` lists one map's replays, and the studio's **This map** tab follows the map open in osu! through `/websocket/v2/subscribe`.

The preview plays the first track's song in sync with the picture. It starts muted; the mute button in the top bar is remembered between visits (`localStorage`, a plain boolean).

## Output size, defaults and presets

The resolution picker offers common sizes in 16:9, 16:10, 21:9, 32:9, 4:3, 9:16 (vertical), 4:5 and 1:1, plus a custom width × height. Sides must be even and 64–7680 px, and a frame may hold at most 7680×4320 pixels; the service enforces the same rule. Named custom sizes, the last size used and the chosen layout are stored in the tool's data folder (`sizes.json`, routes `/v1/sizes`). The preview shows the frame at its own aspect ratio, as large as the centre panel allows; it renders at most 1920 px on the long side, while MP4 and WebM exports use the full size.

Layouts follow the frame's shape. One track always fills the frame. **Side by side** is a row, or a column on a portrait frame; **Stacked** is always a column; **Grid** picks the column count whose cells have the largest short side. **Auto** (the default) picks the column count that draws the smallest playfield largest, from each track's measured playfield: taiko strips stack, mania stages and osu! fields sit side by side when that makes them bigger, and two osu! fields stack on a square frame. Cells are separated by 8 px.

A render runs from lazer's gameplay start (two seconds before the first object, or earlier when the map's `AudioLeadIn` asks for it, never after the song's start) to the last object plus the outro. Like lazer's player, the picture comes in from black (250 ms hidden, then a 250 ms fade) and fades out at the end of the outro; the song fades with it. **Outro** and **Fade** in the Output panel override the defaults for this composition.

Settings the dashboard can edit without opening the studio:

- `resolution` and `fps`: defaults for new compositions and the CLI.
- `outro_ms` and `fade_ms`: time after the last object and the fade at its end; lazer shows results 1250 ms after the last object, fading out over the last 250 ms.
- `output_dir`: where file names are written; when empty, the Videos folder (XDG `user-dirs.dirs` on Linux, `%USERPROFILE%\Videos` on Windows).
- `ffmpeg_path`: the FFmpeg executable; when empty, `VOSU_RENDER_FFMPEG`, then `ffmpeg` on PATH.
- `encoder`: `auto` (default), `hardware`, or `software`. The studio's Output › Advanced › MP4 encoder can override it for one job. Auto tests the actual GPU encoder at the requested size, then falls back to software; hardware fails with an actionable error if none works. Jobs report the selected encoder, not merely the requested preference.
- `parallel_jobs`: `0` (auto) chooses from CPU cores and output resolution, capped at four workers without overlays or eight with overlays; `1` disables partitioning, and `2`–`8` explicitly selects worker count. A render request may override the setting with `parallel_jobs`. Reduce it on machines with limited RAM, VRAM, or encoder sessions.
- `render_gpu`: optional NVIDIA PCI bus id (for example `0000:01:00.0`), empty by default so the system chooses. `VOSU_RENDER_GPU` overrides it. Explicit selection currently requires Linux, NVIDIA's host driver, and `bwrap` (bubblewrap): the managed Chrome sees only the selected GPU's NVIDIA device and DRM render node, while NVENC receives a UUID-based CUDA mask and `-gpu 0` in that local device namespace. This avoids confusing CUDA ordinals with `nvidia-smi` indices. An unavailable target or unsupported platform fails explicitly; it never silently switches to another GPU. Jobs record the BDF, physical index, UUID, exposed device nodes, and browser adapter information.
- `osu_dir`, `songs_dir` and `skin`: an offline stable installation, a Songs folder override, and its fallback skin.

## Skins

Each track picks its skin independently. The track's **Skin** menu starts from the player's preset and can be changed for that replay alone; **Save preset** keeps the choice for the player. The menu lists every source:

- **Current skin**: the osu! client's active skin. For stable, the service reads the skin folder vosu reports (or the `skin` name under a configured `osu_dir`). For lazer, it reads the skin's files through vosu's public `/files/skin/<path>` route, guided by the `GET /files/skin/` descriptor (`{client, name, files, builtin}`). lazer's built-in skins (argon, argon-pro, triangles, legacy) have no files. For those, the studio and the MP4 export use render-core's own drawing of that built-in (`builtinSkin`), and the UI says so. When no current skin is reported, tracks use the classic look.

  File skins of any source fall back to render-core's classic (`legacy`) drawing for elements they do not provide (`withFallback`), as the clients do.
- **lazer**: skins in lazer's library, listed and read through the optional **Lazer library** tool (`GET /tools/lazer-library/api/v1/skins`, then `…/skins/<id>/file/<name>`), read-only. Presets and `--skin` refer to them as `lazer/<id>`. Ids and file names that could leave the library are rejected. Without the library tool the group is empty.
- **osu! Skins folder**: any folder under the stable installation's `Skins` directory.
- **Built-in**: render-core's drawings of lazer's Argon, Argon Pro, Triangles and Classic looks, as `builtin/argon`, `builtin/argon-pro`, `builtin/triangles` and `builtin/legacy`.
- **Imported .osk**: archives imported with the studio's **Import .osk** button (Output › Skins) or with `vosux replay-renderer skins import <file.osk> [--name NAME]`. They are unpacked into the tool's data directory (`skins/<name>`), never into osu! folders; re-importing a name replaces that copy only after the new one is complete. Presets and `--skin` refer to them as `imported/<name>`; `skins list` and `skins delete` manage them.

Files in skin folders (stable, current stable skin, imported) are matched ignoring case, as the clients do: skins mix `Skin.ini`, `Mania-Key1.png`, … while the renderer asks in lower case, and on case-sensitive file systems an exact match would drop a skin's configuration and images, so the same skin would draw differently from a stable folder than from lazer.

vosu forwards at most 1 MiB per request body, so imports are sent as ordered parts: `POST /v1/skins/uploads?name=&size=` (archives up to 512 MiB) returns `{upload, part_size}`, each `POST /v1/skins/uploads/<id>?offset=<n>` appends one part, and `POST /v1/skins/uploads/<id>/finish` validates and unpacks (no unsafe paths or symlinks, at most 20 000 entries and 1 GiB expanded). At most four imports run at once; parts idle for 30 minutes are discarded when the next import starts, and every unfinished upload is cleared when the service restarts.

## Per-replay settings schema

`render-settings.json` is the authoritative machine-readable schema, consumed by both the Rust service/CLI validator and the studio control generator. Every entry declares key, label, applicable numeric rulesets (0 osu!, 1 taiko, 2 catch, 3 mania), inclusive bounds, UI step and default. Presets retain values by key. Toggles use numeric **0/1** so CLI arguments and existing preset files share one representation.

- `mania.scroll_speed`: mania display scroll setting; e.g. change 33 to 27 without changing input timings.
- `note_speed`: independent mania/taiko movement multiplier.
- `background_dim`: 0 shows the map background, 1 blacks it out. Skin stage elements retain their own opacity.
- `cursor.size`, `cursor.trail_ms`: the osu! cursor's scale (lazer's gameplay cursor size) and, for skins without a cursortrail image, the length of a plain look-back trail. Skins with cursor images get lazer's cursor and trail (below). Trails are resampled from recorded replay coordinates, never accumulated from preview history.
- `hit_lighting`: lazer's hit lighting: osu! lighting under judgements, catch's explosions on the catcher, mania's LightingN per hit and hold lighting.
- `taiko.top_area`: the taiko playfield's top area (the strip above the notes), on by default.
- `playfield.scale`, `playfield.x`, `playfield.y`: per-replay playfield scale and centre offsets in cell widths/heights. At scale 1 the playfield's visible extent (a mania stage, the taiko strip, the osu!/catch field), measured from what the renderer draws, fills its layout cell's height, or its width when the cell is narrower than the playfield. The background stays in the cell; playfields may be moved over neighbouring cells. These three are set with the layout editor rather than in **Render settings**.
- `hud.score`, `hud.accuracy`, `hud.combo`, `hud.health`: the built-in HUD layers, switched on per track. Accuracy and score appear only after the replay's stored judgement counts verify, combo only when the combo verifies too. The studio judges every replay itself. osu! and osu!catch replays use the rules of the client that set them (lazer's, or lazer's Classic rules for osu!stable replays): hit windows, note lock, slider heads, ticks, repeats and tails with the 36 ms tail leniency, spinner spins and bonus; catches against the catcher's width. Taiko and mania replays set on lazer use lazer's rules: taiko's windows, wrong colours missing, one press per note per frame, strong notes' second hit within 30 ms, drum roll ticks and alternating swells; mania's windows (with Classic, rate, Easy and Hard Rock), note lock per column, and holds as a head, a tail released with 1.5× leniency (capped at meh after a missed head or a dropped hold) and a body that breaks combo when dropped. Replays store whole milliseconds, so a mania release that lands within half a millisecond of a tail window edge is taken on the side lazer's stored statistics say. Taiko and mania replays from osu!stable use stable's rules, described below. Accuracy then follows that client (lazer counts slider ticks and tails), and the score is the client's own (standardised for lazer, ScoreV1 for stable) whenever the simulated total equals the recorded one; otherwise, and for stable taiko and mania (whose scores are not simulated), the score runs through the judgements to the replay's recorded final score. lazer replays are also checked against the statistics lazer stores with them (taiko and mania: the graded results; bonus and hold-body counts are reported as notes).

  The map is built from the replay's full mod list with lazer's settings: Difficulty Adjust (including extended limits; taiko scroll speed, catch hard-rock offsets), custom rates with adjust pitch (the song's pitch follows the rate for Nightcore, Daycore or adjust pitch), Easy and Hard Rock per ruleset (mania keeps OD and scales its windows), Mirror, seeded Random (mania columns and taiko colours, with .NET's generator), taiko Swap, and mania Invert, Hold Off and No Release. Replays on osu! maps play the map converted to their ruleset as lazer converts it (`packages/ruleset-convert`): key mods and Dual Stages choose mania's layout, converts use stable's fixed mania windows, and overlay pp rates the converted map. Replays whose judgements depend on mods it cannot reproduce (osu! Random positions, unseeded osu!stable Random, Wind Up/Down, Adaptive Speed, Relax, Autopilot, autoplay, object-moving fun mods) are not judged and say so.

  osu!stable's source is not public, so its taiko and mania rules come from the osu! wiki (windows) and from measuring candidate rules against the header counts of the user's own stable replays, keeping a rule only when it raised the number of replays whose counts match. Replay frames are decoded the way lazer reads stable replays (integral deltas, stable's lead-in fix-ups, the two `(256, -500)` lead-in frames dropped, frames that go back in time skipped). Taiko: the miss window includes its last whole millisecond and a note stays open until it passes (a late press there misses the note rather than reaching the next one); notes take presses before drum roll ticks; in a frame that presses both colours the colour not matching the next note applies first and the other colour carries on to the following note; with ScoreV2 every drum roll and completed swell also counts as a 300. Mania: windows in whole real milliseconds (`64 - 3 × OD` and so on, the fixed table for converts, Hard Rock/Easy dividing/multiplying by 1.4 before truncating, rate mods leaving them unchanged in real time); a press reaches the first open object in its column, does nothing more than a miss window early, misses from the meh window outwards, and (except with ScoreV2) cannot reach a note before the previous one in its column has started; a note is missed from the ok window late. A hold note is one judgement from the head error and the head + tail error (1.2/2.4 × perfect, 1.1/2.2 × great, 2 × good and ok, else meh); a press more than a meh window early counts the whole hold as its head error; a hold released before its tail's meh window is dropped, picked up again by a later press (with that press's head error, capped at good) or else missed. While a hold is held its combo rises every 100 map milliseconds from the press until its end, and dropping it breaks the combo. These hold-note details follow the approach of Mania-Replay-Master (Mania-Visualization-Project, Apache-2.0; no code taken), which matched the user's replays better than the alternatives tried. With ScoreV2, the perfect window is `difficultyRange(OD, 22.4, 19.4, 13.9)`, there is no column lock, and heads and tails are judged separately (tails with 1.5× windows, at most meh after a missed head or a dropped hold). With a rate mod stable judged at fractional map times that the replay rounds, so a judgement within half a map millisecond of a window edge is placed on the side the replay's header counts say.

  Health follows the recorded life graph (osu!stable replays). lazer replays carry none, so the bar shows lazer's health simulated from the verified judgements: osu!'s draining processor (the stable-like one with Classic's classic health), catch's and mania's legacy draining processors (mania never drains) and taiko's accumulating one, with lazer's drain rate search over the map, No Fail, Easy's extra lives, and Sudden Death/Perfect. A lazer play whose simulated health runs out stops being judged there, as lazer stops it. For osu!stable replays the same simulation is compared with the recorded graph during verification. Overlay pp is rated with lazer's own mod list (so Classic removes slider head accuracy for lazer scores), its rate and Difficulty Adjust values. By default they follow lazer's legacy/argon HUD: health bar top left, score top right with accuracy right under it, combo bottom left, each 20 units in from the cell's edges and never overlapping. Units are the cell's short side over 1080, so the HUD keeps its proportions in any cell. `hud.<layer>.dx`/`.dy` are the layer's distance from its corner in those units and `.scale` its size; the layout editor sets them. (Presets holding the earlier fraction-based `hud.<layer>.x`/`.y` drop them and use the defaults.)

Judgements are drawn in the playfields as lazer draws them with legacy skins, driven by the simulated results (every replay, verified or not; only the HUD numbers wait for verification): osu! hit/miss pieces with particles and lighting at the object, taiko explosions under the hit target with hit notes leaving at their hit and missed ones scrolling on, mania judgements at the skin's ScorePosition with LightingN per hit, and catch hit lighting and the combo counter on the catcher, whose idle, kiai and fail states follow the results. Images a skin lacks come from the built-in classic look. Nothing else is drawn on top of the playfields: there is no name header, judgement counter, key overlay or progress bar. Anything more comes from an overlay page. Presets saved by earlier versions keep working: settings this version no longer has (`hud.player`, `hud.judgements`, `key_overlay`) or values outside a setting's range are dropped when the presets load.

The replay's own input is drawn too, as lazer draws it with legacy skins: osu!'s playfield sits 8 osu! pixels lower, as in lazer's gameplay, and the skin's cursor turns, expands on each press and leaves its cursortrail; taiko's input drum halves flash on every press, and with the top area on the skin's pippidon mascot idles, kiais and fails (clearing every 50 combo); the catcher follows the replay, leaving dash and hyper-dash trails and hyper-dash after-images, with caught fruit stacked on the plate and exploding or dropping when the combo ends; mania's key images and column lights follow the presses and releases. The kiai glow under taiko's hit target shows during kiai. Lazer stacks plate fruit at random; the renderer uses the same rule with a fixed seed, so exports are reproducible.

Each track card's **Layers** group switches the built-in layers (Score, Accuracy, Combo, Health bar, Hit lighting, taiko's Top area) and every overlay for that track.

Player presets use exact player names, including Unicode, and apply automatically on import. A per-render setting overrides the preset; the preset overrides tool defaults. Different-difficulty grouping requires the same positive BeatmapSetID, and all tracks must use the same rate. Audio comes from the first track.

### Layout editor

Point at the preview to see the boxes of playfields, HUD layers and overlays; nothing of the editor shows otherwise, so the preview is the export's picture. Click a box to select it. Drag to move; drag a corner to resize (playfields and HUD layers always keep their aspect ratio, overlays with Shift). Edges and centres snap to the canvas and the layout cells; hold Alt to move or resize freely. Arrow keys nudge by one output pixel, Shift+arrow by ten. **Layout** in the Output panel shows the selection's X, Y, W, H, scale and opacity and keeps them in sync (overlays: X/Y from the cell's corner); **Reset** returns it to its default. Positions are stored per replay (playfields, HUD layers) and per overlay layer and are used unchanged by both exports.

### Composition inspector (development aid)

Off by default. Adding `?inspect` to the studio's URL draws, over the preview and into MP4 exports started from that page: cell bounds, the 5 % action-safe and 10 % title-safe areas, every layer's box with its paint-order number and name (backgrounds, playfields, HUD layers, overlays), and a legend with the frame's clock (time, start, end, fade) and per-layer draw times. Render requests carry it as `inspect: true`.

## Export runtimes

The Rust service drives Chrome Headless Shell and streams fixed-clock RGBA frames to external FFmpeg. On first native render, it downloads the release-pinned **156.0.8078.47** Linux/Windows x86_64 archive from Google's Chrome for Testing storage, checks an embedded SHA-256 before extraction/execution, rejects escaping paths/symlinks and oversized archives, and caches the runtime with its complete upstream `LICENSE.headless_shell`. `VOSU_RENDER_CHROMIUM` explicitly overrides this managed runtime for offline/custom installations (the headless shell or a full Chrome/Chromium run with `--headless=new`; each overlay page gets a headless window of its own, since full Chrome's background tabs are hidden and produce no frame to capture once their picture stops changing; pages that use generic font families such as `monospace` draw with that browser's default fonts). **Full Chrome leaves WebGPU canvases out of its captures**: an overlay that draws with WebGPU (for example EZ2ON Key Visualizer with its WebGPU renderer) exports blank there, while WebGL canvases and the page's other content are captured, and the managed headless shell captures WebGPU too. The renderer tells you: with a custom browser set, the studio's Output panel names every overlay whose live preview created a WebGPU canvas before you press **Render MP4**, and a render whose browser reports itself as full Chrome (`Browser.getVersion`) names the overlays that drew with WebGPU in the job status, the CLI output and the final job result (it keeps rendering). Unset `VOSU_RENDER_CHROMIUM`, or choose WebGL in the overlay's settings where it offers one; `VOSU_RENDER_FFMPEG` selects FFmpeg. No user-installed Chromium or Node is required. Initial rendering requires network access unless the runtime is cached or overridden; system libraries/sandbox support still follow the OS browser requirements. Native output is MP4 with H.264/AAC. FFmpeg remains external and is never bundled; its libx264 encoder (the software fallback and the Discord fit) is GPL, so mind the FFmpeg build's licence if redistributing it.

Browser export (the **Export WebM** button) uses WebCodecs VP9/Opus and writes WebM, with OfflineAudioContext rate/gain mixing; "Export for" does not apply to it. Both paths use the same absolute map-time compositor and GPUTexture readback; preview frames are staged before publication so asynchronous readback cannot blank the currently displayed frame.

### MP4 compatibility and "Export for"

Every native MP4 is made to play and upload anywhere: H.264 High profile with the lowest level that holds its size and frame rate (Rec. ITU-T H.264 Table A-1; 4.1 at 1080p30, 4.2 at 1080p60, 5.2 at 2560×1080@120), yuv420p converted with the BT.709 matrix and tagged BT.709 limited range, closed one-second GOPs, AAC-LC 48 kHz stereo, and `+faststart` (the index before the media data) applied to the final file, after parallel segments are joined. NVENC uses the same profile and level with B-frames that are never references, so players without B-pyramid support decode it. Sides are always even.

**Export for** in the Output panel (and the `export_for` / `discord_mb` settings, `vosux replay-renderer render --for x|discord|youtube [--discord-mb 20|50|1000]`) adds a site's limits. The studio remembers its choice and shows the result under it (size, frame rate, Discord bitrate) or a one-line warning:

- **Standard**: the output size and frame rate as set, CRF 18 (CQ 18 on hardware), 192 kbps audio.
- **X / Twitter**: [X's upload limits](https://help.x.com/en/using-x/x-videos) (the size, aspect, frame rate and bitrate limits are in that page's FAQ, e.g. the [Indonesian version](https://help.x.com/id/using-x/x-videos)): at most 1920×1200 landscape or 1200×1900 portrait, aspect ratio 1:2.39 to 2.39:1, 40 fps, 25 Mbps; without Premium 140 s and 512 MB. The frame is scaled to fit (wider or taller frames are letterboxed to 2.39:1 first), faster frame rates are rendered at the largest whole fraction of the rate within 40 fps (120 → 40, 60 → 30, 144 → 36; otherwise 30), video is capped at 20 Mbps and audio is 128 kbps. Compositions longer than 140 s still export, with a warning.
- **Discord**: fits the chosen [Discord file size limit](https://support.discord.com/hc/en-us/articles/25444343291031-File-Attachments-FAQ): 20 MB (free), 50 MB (Nitro Basic) or 1 GB (Nitro), counted in decimal megabytes with a 3 % margin. After the normal export, the file is re-encoded with two-pass x264 at the bitrate the duration allows (96 kbps audio at 20 MB, else 128 kbps), at most 60 fps (the largest whole fraction of the rate, so 120 → 60), scaled down (not below 360 px on the short side) when those bits cannot carry the full frame, then checked; an overshoot is retried at a lower bitrate. A composition too long for the size fails with a message instead of an unwatchable file.
- **YouTube**: no limits; CRF/CQ 14 and 320 kbps audio.

### Export throughput and diagnostics

Native MP4 uses H.264: auto probes NVENC first, then Intel Quick Sync/AMD AMF on Windows or the available VAAPI render devices on Linux, and finally libx264. Hardware is tested with an actual RGBA frame at the output size, frame rate, profile and level before accepting input; an FFmpeg build listing an encoder is not enough to establish driver/device availability. Software explicitly selects libx264 (`veryfast`, CRF 18 by default; see "Export for"). Hardware uses comparable constant-quality settings. A device failure after encoding starts fails the job rather than silently dropping frames or changing codecs mid-file.

The private browser avoids GPU-vsync waiting, but retains Chrome's frame-rate scheduler so animation callbacks cannot starve the virtual-time budget. Overlay pages still receive every fixed-clock frame and advance their timers at the requested cadence; their state/clock/capture protocol is batched across independent pages, and PNG screenshots retain lossless pixels and transparency. Identical overlay PNGs reuse the decoded bitmap. Every player's GPU draw/readback is submitted before waiting for the GPU; CPU-only intermediate canvases avoid uploading readback pixels just to read them back again. Export compositions do not copy a full frame to a visible preview canvas. Native export overlaps one ordered frame upload with the following frame's work, with bounded buffering and encoder backpressure; preview publication remains atomic.

Completed native jobs include `encoder`, `seconds`, `render_fps`, `startup_ms` (loading, replay simulation, scene compilation/probing), `timings_ms` (scene CPU/submission, GPU/readback wait and copy, playfield composition, overlay clock/capture/decode/composition, final pixels/fade, transfer/encoder backpressure), and `encoder_drain_ms`. `timings_ms.gpu` is the GPU render-pass timestamp total when the adapter supports timestamp queries, otherwise null; it is included in readback elapsed time, not an additional wall-clock stage. Transfer overlaps subsequent rendering, and players' GPU work overlaps, so stage totals must not be added to reconstruct job wall time. Browser WebM retains VP9/Opus and now uses dequeue-based bounded backpressure, flushing only at end-of-stream instead of repeatedly draining the encoder.

Parallel native exports split the exact integer frame range into contiguous partitions, each with its own private browser, overlay origins, and encoder. Overlay workers replay all earlier deterministic state/clock ticks without screenshots before capturing their partition, preserving history-dependent widgets. Segment video uses closed GOPs and is concatenated without re-encoding; the soundtrack is encoded once against the complete original output clock, avoiding AAC segment gaps or repeated entry fades. Running and completed jobs report `parallel_jobs` and the actual `encoder`; parallel results contain per-worker profiles in `segments` and final `mux_ms`. Stage totals overlap across workers and must not be added to obtain wall time.

Overlay partition sizes are slightly weighted toward earlier workers to account for later workers replaying more history. Every frame remains on the same absolute clock. The concat list supplies exact frame-derived segment durations rather than MP4's millisecond-rounded container durations, so partition joins do not shift timestamps.

## Overlay pages (native MP4)

**Add** in the Output panel's **Overlays** opens a list of the overlays installed in vosu (`GET /tools/_host/v1/overlays`) with a search field: type to filter by nickname, name, author or folder (case and accents ignored; every word must match), use the arrow keys and Enter to pick. Each entry shows the dashboard nickname (else the name), the folder, the author and the page size. At most 80 matches are shown at once, with a count of the rest. Below the list, **Open .html file…** takes the absolute path of a single HTML overlay page, served from its own folder, and **Custom folder…** an absolute folder with `index.html` (the only options on vosu builds without the overlay list).

A newly added overlay is placed at the first spot (top to bottom, left to right) where its page covers no playfield, HUD layer or other overlay in any player's cell; without one it goes under the health bar. **Reset** places it the same way. An overlay added to the composition shows for every player, each copy in that player's cell at the layer's X/Y from the cell's corner, driven by that player's replay; a track card's checkbox switches it off for that player. A layer's page size starts from the overlay's `metadata.txt` resolution; once resized, the size is remembered per overlay in the tool's data folder (`sizes.json`). Each layer has an independent page size, position, scale and opacity. The preview draws the overlays live (see "Live overlay preview"); the native render captures the same pages. Browser-only WebM export explicitly rejects overlay layers instead of silently omitting them.

The CLI accepts repeated `--overlay /absolute/overlay-folder-or-page.html` arguments. A folder must contain `index.html`; CLI layers default to the full output viewport at (0, 0). The service render request accepts `overlays: [{folder,width,height,x,y,scale,opacity,settings,tracks}]`, where `folder` may also be an `.html` file and `tracks` (absent: all) lists the tracks showing the layer. At most 32 overlay pages run per render (overlays × players).

### The overlay server

Each player's overlays get their own throwaway loopback server (`src/overlays/server.rs`) that speaks vosu's overlay-facing protocol, answered from that player's replay instead of the game. Shapes follow vosu (`dev/1.2.0`, `src/server/routes.rs` and the API builders): every field vosu reports is present, with vosu's idle values where a replay has nothing to say (the templates in `src/overlay-api/` are vosu's own wire fixtures).

| Route | Answer |
| --- | --- |
| `/json/v2`, `/websocket/v2` | vosu v2 document: state `play`, beatmap metadata and stats (stars and max combo rated with rosu-pp, object counts, BPM, `hitWindow` from the windows the judging used, in real milliseconds), `play` (hits, accuracy, combo, score, health 0-100, `hitErrorArray` in gameplay milliseconds, mods, rank, unstable rate, pp), `keys` (`k1`/`k2`/`m1`/`m2` and `all` with counts and press/release times), files and direct paths |
| `/json/v2/precise`, `/websocket/v2/precise` | keys, hit errors, press and release hit errors |
| `/websocket/v2/subscribe` | vosu's selected-field protocol: one JSON-pointer list (1-256, non-overlapping) within 5 s, then `[0,rev,[[i,v]…]]` and change-only `[1,rev,[[i,v]…],[removed…]]`; errors `[2,code,message]` close with 1008 |
| `/json`, `/ws` | gosu v1 projection of the same state |
| `/json/sc`, `/tokens` | StreamCompanion projection |
| `/websocket/commands?l=<overlay>` | `getSettings:<overlay>` answers `{"command":"getSettings","message":{…}}` with the overlay's effective settings (below); another overlay's name answers vosu's `Wrong overlay` error; `updateSettings` echoes; `saveSettings` and `applyFilters` are accepted without effect (read-only) |
| `/files/beatmap/file`, `…/audio`, `…/background`, `/backgroundImage`, `/files/beatmap/<path>`, `/Songs/<map folder>/<path>` | the replay's map and its folder's files |
| `/files/skin/`, `/files/skin/<path>` | that track's skin, as vosu describes and serves the current skin |
| `/tools/mania-ratings/api/…` | the local ratings endpoints `ratings-timeline` reads |
| `/<overlay id>/…` | the overlay's own files at the path vosu serves them, HTML ending with vosu's `window.COUNTER_PATH` |

Anything else answers 404 (WebSocket paths do not upgrade), as vosu does for unknown routes, so no page waits on a route the server lacks. `/api/calculate/pp` is not served.

Whole-document streams (`/websocket/v2`, `/ws`, `/tokens`) send on connect and then, like vosu with its default `POLL_RATE` and `PRECISE_DATA_POLL_RATE`, at each poll every 150 ms (precise: 10 ms, so every frame) of render time from the connection, when the document changed; `/websocket/v2/subscribe` sends every change, as vosu's change-only subscriptions do. Overlays on different feeds therefore disagree briefly, as with vosu: a page on `/websocket/v2` shows counts up to 150 ms older than one on `/websocket/v2/subscribe`.

**Settings.** An installed overlay (its folder matches vosu's overlay list) reads the values vosu itself would give it: the service asks vosu's `/websocket/commands` once per render or preview, exactly as the overlay does, so the user's saved values for the active profile apply over the overlay's defaults. Other folders read their `settings.json` defaults. A layer's own `settings` (render request) apply on top. Nothing is written back.

**State.** Gameplay values come from the studio's judgement simulation, including replays whose simulation does not reproduce the recorded counts exactly (the track note says so; overlays expect numbers). Replays without a simulation keep vosu's idle values. pp is calculated with rosu-pp from those counts (lazer's acronyms, rate and Difficulty Adjust values for lazer replays). This is a replay, not the game: settings, profile, leaderboard and tourney fields keep vosu's idle values.

**Render clock.** Pages run on the export's clock: `Date.now`, `performance.now`, `requestAnimationFrame` timestamps and page timers (`setTimeout`/`setInterval`) all follow the frame time, so a page's retries and timeouts happen when they would during play, not all at once while the page loads. Animation frames follow the export's frames: once a page has loaded, every `requestAnimationFrame` callback runs exactly once per output frame, after that frame's data arrived and before it is captured, with the frame's time (output frame times step by exactly 1000/fps ms), so pages animate and measure their own frame rate at the video's rate. Chrome's own frames (paced by virtual time and the compositor, several or none per output frame) never call page callbacks once the page has loaded. After every published state, each stream socket ends its frames with a sync marker that the injected clock consumes before page listeners. A frame is captured once every open stream socket has seen its marker, every `getSettings` sent has its answer, fetches are drained and declared web fonts have loaded (they load with the page). Chrome does not complete WebSocket handshakes while a page's virtual time is paused, so while pages settle their virtual time is nudged by 0.01 ms every 25 ms; sockets a page opens mid-frame (rolling subscriptions, reconnects) connect. A page that still does not settle within 20 s fails the render with its name and what it waited for, e.g. `EZ2ON Timing Bar: no response to getSettings`, `…: /websocket/v2/subscribe opened but never subscribed`, `…: request /json/v2 never finished`, `…: web fonts never finished loading`; every browser protocol step is bounded too.

### Live overlay preview

While a composition has overlays, the studio starts a preview (`POST v1/preview` with the layers and each track's map, mods and initial state): the same overlay server, one per track, without the render clock or sync markers. Each overlay page is an iframe over the preview at its box, scaled and faded like the export composites it, so the preview shows the overlays drawn. The studio sends each track's state for the time on screen (`POST v1/preview/<session>/state`, at most every 33 ms while the clock moves, once a second while still), pages run on real time. A preview that is not playing reports the game paused (`game.paused`), as vosu does for a paused play, so pages stop their clocks and the still time before playback does not count as an animation frame. Pages load one after another (Chrome opens WebSockets to one address one handshake at a time; all pages at once kept some sockets connecting longer than tosu's command helper retries `getSettings`). Changing the overlays, tracks, skins or page sizes starts a new preview; one preview runs at a time and an idle one ends after ten minutes. The servers accept a document navigation from the studio's page; every other request must come from the server's own origin.

Pages render in the private browser and are composited into the same output frame. Fetches and resources outside a page's private origin and nonlocal WebSocket connections are blocked; pages never receive vosu host credentials or connect to the live game.

## Local verification inputs

`test-fixtures/` is an ignored, non-packaged directory for local copies of user-owned replays/maps/skins. Keep real inputs there rather than relying only on `/tmp`; never commit or distribute them. Run replay tests with `REPLAY_FIXTURES=<absolute>/test-fixtures/real` and `REPLAY_CORPUS=<absolute>/test-fixtures/corpus` when those local fixture sets are available. Synthetic telemetry tests are under `web/test/`.

For a development checkout, run `cargo build --locked -p vosu-replay-renderer`, then copy `target/debug/vosu-replay-renderer` (`.exe` on Windows) into `tools/replay-renderer/bin/` before starting `vosu --tool tools/replay-renderer`. Development executables are ignored; the release packager supplies the compiled binary automatically.
